# US-002 — Replace regex YAML parser with real parser and add schema validation

> Generated by Doc-Gen Agent on 2026-05-03T00:00:00Z
> Parent: SPEC-001 | Task: T-002 | Status: done

## Who uses this and why

Any maintainer who runs `conformance/runner.mjs` — whether locally or in CI — needs
confidence that YAML frontmatter is parsed correctly. The previous implementation
used a regex over lines 79-89 of the runner to extract key-value pairs from YAML
frontmatter. That regex could not handle multi-line strings, flow sequences, or
anything beyond the simplest scalar values. A spec file with an array value or a
multi-line description would be silently misread, making the runner's schema checks
unreliable. This story replaces that brittle path with a proper implementation and
adds a dedicated validation mode that CI can call directly.

## What was built

`conformance/runner.mjs` was modified in two ways.

First, the regex YAML parser was removed and replaced by an in-file recursive-descent
YAML parser (`parseYaml`, located at line 337, with supporting functions `parseBlock`
and `parseScalar`). The implementation handles indented block mappings, block
sequences, quoted strings, multi-line folded/literal scalars, boolean, integer, float,
and null scalars. A companion function `parseStackMd` (line 352) extracts and merges
all fenced YAML code blocks from `stack.md`. The parser is intentionally scoped to
the YAML surface actually used by `schemas/v1.0.0/` artifacts — it is not a
general-purpose YAML 1.2 library. A detailed rationale comment at the top of the
file explains why no third-party dependency was vendored (the codebase enforces a
zero-dep posture; there is no `package.json`).

Second, a `--validate-schema <spec-dir>` CLI flag was wired in. When invoked, the
runner:

1. Resolves the target spec directory path.
2. Loads all five schema files from `schemas/v1.0.0/` using the in-file JSON Schema
   validator (line 366+), which supports the exact keyword set used by the schemas:
   `type`, `required`, `properties`, `additionalProperties`, `enum`, `const`,
   `pattern`, `format` (date/date-time), `oneOf`, `items`, `minLength`, `minimum`,
   `uniqueItems`.
3. Walks SPEC-*.md, stories/US-*.md, tasks/T-*.md, the project's `input/tech/stack.md`,
   and any `.pipeline-shipped` marker in the directory.
4. Reports each file as a pass or fail with per-field error messages.
5. Exits 0 only if all present required artifacts are valid; exits non-zero on any failure.

The `.pipeline-shipped` marker is optional — its absence is reported as a skip, not
a failure.

## Drift note — spec vs. implementation

The T-002 technical spec suggested using `js-yaml` or a similar library for the YAML
parser. The actual implementation chose a zero-dependency in-file parser instead,
preserving the codebase's no-`package.json` invariant. The functional behaviour
matches the spec; only the implementation approach differs. This is documented
explicitly in the runner's header comment and was accepted by the QA gate.
