## What this feature is

planr-pipeline is a Claude Code plugin, not a traditional application. There is no
HTTP server, no compiled build, and no database. The "source code" is primarily
Markdown files (agent contracts, protocol documents, templates) plus a single Node.js
script, `conformance/runner.mjs`, that has no npm dependencies.

SPEC-001 added a schema layer to this codebase: a directory of JSON Schema files that
formally define every artifact the pipeline reads and writes, and an extended
conformance runner that can validate any spec directory against those schemas.

## Data flow — `--validate-schema` mode

```
Maintainer / CI
  │
  └─► node conformance/runner.mjs --runtime <runtime> --validate-schema <spec-dir>
        │
        ├── Load schemas/v1.0.0/*.json  (5 files)
        │     spec.schema.json
        │     story.schema.json
        │     task.schema.json
        │     stack.schema.json
        │     pipeline-shipped.schema.json
        │
        ├── Walk spec directory
        │     SPEC-NNN-{slug}.md        → readFrontmatter() → validate() → spec schema
        │     stories/US-NNN-{slug}.md  → readFrontmatter() → validate() → story schema
        │     tasks/T-NNN-{slug}.md     → readFrontmatter() → validate() → task schema
        │
        ├── Validate stack
        │     input/tech/stack.md       → parseStackMd()    → validate() → stack schema
        │
        ├── Validate completion marker (optional)
        │     .pipeline-shipped         → readFrontmatter() → validate() → pipeline-shipped schema
        │
        └── Aggregate results
              0 failures → exit 0
              N failures → print per-field errors, exit 1
```

Both `readFrontmatter()` (for YAML frontmatter blocks) and `parseStackMd()` (for
fenced YAML code blocks inside Markdown) feed the same `parseYaml()` function. The
JSON Schema validator is also in-file; it supports only the keyword subset used by
the shipped schemas. See `conformance/runner.mjs` lines 337-600 for the implementation.

## Dependencies on other features

SPEC-001 does not add any runtime dependencies. The conformance runner remains stdlib-only
(Node `fs`, `path`, `child_process`, `os`, `url`).

The schemas are consumed by:
- `conformance/runner.mjs` at validation time (this feature)
- `docs/protocol/spec-artifacts.md` as linked references (this feature)
- Any future tooling that reads `schemas/v1.0.0/` (e.g. the planr CLI, IDE plugins)

The feature depends on `input/tech/stack.md` for `BuildCommand` and `TestCommand`
during CI. There is a known gap: `input/tech/stack.md` currently lacks a
`schemaVersion` field, which causes the runner to report one INFO-level finding when
validating against `stack.schema.json`. This is pre-existing and out-of-scope for
SPEC-001; it will be resolved by adding `schemaVersion: "1.0.0"` to that file
(candidate: SPEC-007).
