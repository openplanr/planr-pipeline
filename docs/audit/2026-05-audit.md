## What this codebase actually is — corrected framing

Before any verdict, the audit framework has to be re-grounded. The audit prompt was written generically (TS line counts, package.json, Zod schemas). **This repo is none of that.** It is a Claude Code plugin made entirely of:

- 8 agent definitions (markdown + YAML frontmatter; `tools:` is the security boundary)

- 2 slash commands (markdown — these are long prompts the model executes verbatim)

- 5 templates (`.tpl` and `.md`)

- 5 stack hint files

- 7 protocol/docs files

- 1 hooks config (`hooks/hooks.json`, 15 lines, one Stop hook)

- 1 conformance test runner (`runner.mjs`, 345 lines — the only executable code in the repo)

- A plugin manifest (`.claude-plugin/plugin.json`, 21 lines)

There is no `package.json`, no TypeScript, no source tree. **Every "code quality" complaint must be re-cast as "prompt clarity," "schema discipline," or "doc/template consistency."**

The audit below is recast accordingly. I am not going to pretend the rubric fits when it doesn't.

There is no `package.json`. The conformance runner uses **only Node stdlib** (`node:child_process`, `node:fs`, `node:os`, `node:path`, `node:url`). **Zero third-party deps. This is the cleanest possible state — no action needed.**

### 1.3 Schema & contract audit

**This is the heart of the audit.** The artifact schema (SPEC frontmatter, US frontmatter, Task frontmatter, `.pipeline-shipped` marker) is the load-bearing cross-runtime contract. Today it lives in:

- [docs/protocol/spec-artifacts.md](docs/protocol/spec-artifacts.md) (prose tables — canonical)

- [docs/spec-anatomy.md](docs/spec-anatomy.md), [docs/us-anatomy.md](docs/us-anatomy.md), [docs/task-anatomy.md](docs/task-anatomy.md) (more prose, partially overlapping)

- [agents/specification-agent.md](agents/specification-agent.md) (agent that writes US/Task — has its own copy of the shape)

- [conformance/runner.mjs:79-89](conformance/runner.mjs:79) (regex-based YAML parser; verifies a different subset of fields)

**There is no machine-checkable schema artifact (JSON Schema, Zod, even YAML `$schema`).** Every reader/writer reimplements parsing in prose. The protocol doc itself notes `schemaVersion: "1.0.0"` is required — but nothing actually enforces that this string is present, much less validates the rest.

## PHASE 2 — VERDICT (Bucket-classified)

### Bucket A — Critical Violations (block other work)

**A1. [commands/plan.md](commands/plan.md) is 680 lines and conflates ten responsibilities.** Sanitization, parsing, plan-mode short-circuit, 5-strategy state machine, framework-scaffolder dispatch, asset stash, mode detection, spec auto-scaffold, self-heal, subagent dispatch, completion contract. The CHANGELOG admits that v0.7.2's plan.md was already failing — the model abandoned mid-task and the v0.7.3 fix piles on a "TodoWrite is mandatory + Completion Contract" preamble. That fix patches the symptom; the root cause is one file doing too much. **Split into orchestrator + named procedure files.**

**A2. No machine-checkable schema for the v1.0.0 contract.** [docs/protocol/spec-artifacts.md](docs/protocol/spec-artifacts.md) is the canonical specification, but it's prose. The conformance runner parses YAML with `^([A-Za-z0-9_]+):\s*(.*)$` ([conformance/runner.mjs:84](conformance/runner.mjs:84)) — a hand-rolled regex that breaks on multi-line strings, arrays, or nested keys. There is no shared validator across runtimes. **A protocol that ships across three runtimes without a schema artifact will drift.**

**A3. [templates/spec.md.tpl](templates/spec.md.tpl) and [templates/spec-driven.md.tpl](templates/spec-driven.md.tpl) describe two incompatible schemas.** spec.md.tpl uses `FeatureName`, `Priority: "P0"`, `PO`, `CreatedAt` (line 13-19). spec-driven.md.tpl uses `id`, `slug`, `priority: "P1"`, `created` (line 1-12). The same `priority` field uses different value formats in the two templates. **Both templates serve real users (default-mode solo-dev path vs spec-driven team-handoff path), so keep both — but reconcile them around a shared v1.0.0 schema.** Either harmonize spec.md.tpl's frontmatter to match the v1.0.0 fields (with default-mode-specific extensions documented in `schemas/v1.0.0/spec-default-mode.schema.json`), or move the divergent header section out of frontmatter and into the body. The two templates can describe two body conventions; they cannot describe two contradictory frontmatter contracts.

**A4. [agents/frontend-agent.md](agents/frontend-agent.md) and [agents/backend-agent.md](agents/backend-agent.md) contradict themselves internally.** Both have a "Path Resolution (NEW in pipeline v0.3.0)" preamble that describes spec-driven paths, then an Inputs table further down ([frontend-agent.md:36-43](agents/frontend-agent.md:36), [backend-agent.md:40-51](agents/backend-agent.md:40)) that hard-codes default-mode paths only. A model reading the agent prompt linearly sees both — the table comes second and looks authoritative. **Tables must reflect the dual-mode reality or default-mode must be removed.**

**A5. R7 ("CLAUDE.md must be current before any subsequent agent run") is aspirational, not enforced.** [docs/rules.md:93](docs/rules.md:93) makes a binding claim. No agent prompt actually verifies CLAUDE.md exists or is current. The snapshot is the _last_ step of /ship, never a precondition. **Either drop R7 or have agents check `git log -1 --format=%cI CLAUDE.md` before they read it.**

**A6. The "default mode vs spec-driven mode" dual path duplicates ~30% of every agent prompt.** Every agent has a Path Resolution preamble, dual Inputs/Outputs tables, dual error-report path conditional. The bloat is a real implementation problem — but **both modes serve different real users** (default = lightweight solo-dev path, spec-driven = formal team/handoff path), so the remedy is **mode isolation, not deletion.** Each agent prompt becomes a thin entry file (~40 lines: name, tools, model, shared preamble, then a `Read` call to load the active-mode file from `agents/modes/<spec-driven|default>/<role>.md`). Things genuinely identical between modes (correction-loop reference, output contract header) live in `agents/modes/shared/`. Net effect: model loads only the relevant mode, not both. Token cost drops, clarity improves, both user surfaces stay. **The protocol layer being spec-driven-only is the protocol's narrowing — not a signal default mode should die.**

**A7. The conformance test only covers spec-driven happy-path with no PNG.** Five strategies in [commands/plan.md:148](commands/plan.md:148) (`CONTINUE`, `BOOTSTRAP_ONLY`, `SCAFFOLD_NODE`, `ASK_MANUAL`, `ASK_STACK`) — only `CONTINUE` is exercised. Three failure modes (db-agent connection failure, designer-agent skip, specification-agent crash) are unpicked. The 3-iteration loop and error-report.md generation are never exercised. **Default-mode is also fully untested.** Conformance is a sticker, not a gate. **Add fixtures (don't remove modes):** `conformance/fixtures/default-mode/`, `conformance/fixtures/with-png/`, `conformance/fixtures/failure-3-iter/`. Each reuses the existing runner harness with mode-specific assertions.

**A8. No Stop hook fires on `/planr-pipeline:plan` abort.** [hooks/hooks.json:9](hooks/hooks.json:9) only handles `.snapshot-pending` for /ship. /plan has equally hazardous half-states (a stash in `/tmp/planr-pipeline-stash/<slug>-<ts>/` after `STAGE_DESIGN_ASSETS` ran, but `RESTORE_DESIGN_ASSETS` did not). **Add a corresponding sentinel for /plan.**

### Bucket B — Structural Debt

**B1. `commands/plan.md` and `commands/ship.md` duplicate "Mode detection + self-heal" verbatim.** [plan.md:443-530](commands/plan.md:443) and [ship.md:20-79](commands/ship.md:20). Two near-identical blocks. Edit one, forget the other → drift. **Extract into a single `docs/protocol/mode-detection.md` referenced by both.**

**B2. The 3-iteration correction loop is described in 6 places** with different wording: [docs/rules.md:68](docs/rules.md:68) (R6), [commands/ship.md:96-104](commands/ship.md:96), [agents/frontend-agent.md:174-192](agents/frontend-agent.md:174), [agents/backend-agent.md:252-270](agents/backend-agent.md:252), [templates/error-report.md:24-44](templates/error-report.md:24), [docs/pipeline-overview.md:159-166](docs/pipeline-overview.md:159). The iteration count (3) and verification command order (Lint → TypeCheck → Build → Test) must agree across all six. **Make rules.md normative; everywhere else links to it.**

**B3. `backend-agent` is two agents in one prompt.** Scaffold mode (Step 0.2 — entity generation from schema.json, output to `output/src/`) and Dev mode (Step 3 — task-driven codegen, output to `src/features/`). They have different inputs, different outputs, and different system prompts. Sharing one `tools:` manifest is fine, but the prompt should be split. **Either: two `model:` configurations sharing tools, or rename to `entity-scaffold-agent` + `backend-agent`.**

**B4. `${CLAUDE_PLUGIN_ROOT}` references are scattered, not registered.** `grep '\${CLAUDE_PLUGIN_ROOT}' -r .` finds the token in 14 files. The runtime-adapters doc says Cursor/Codex must substitute these. The conformance runner checks for leaks in generated rule files (good). **But a `docs/protocol/path-references.md` registry would let a maintainer audit the surface in one place.**

**B5. `stack.md` is parsed by prose-grep, not a parser.** Every agent prompt says "extract `BuildCommand` from stack.md" but there's no parser, no schema, no validation. The user authors free-form YAML inside markdown code fences. A typo (`Build_Command:` vs `BuildCommand:`) silently breaks the correction loop. **Either: validate stack.md frontmatter at the start of each command, or convert to YAML/TOML and parse it.**

**B6. `Active Stacks` mechanism contradicts itself between docs.** [templates/stack.md.tpl:114-118](templates/stack.md.tpl:114) tells users to list `.claude/stacks/backend/nestjs.md`. Agent prompts say to look up `${CLAUDE_PLUGIN_ROOT}/stacks/...` first, then `.claude/stacks/...` overlay. A user copying the template literally will list a path that, if the file doesn't exist locally, doesn't fall back to the plugin default. **Document the precedence in stack.md.tpl too.**

**B7. `hooks/hooks.json` has a single Stop hook with a long inline shell command.** [hooks/hooks.json:9](hooks/hooks.json:9). The compound `test ... && rm ... && echo ... || true` is unreadable and untested. **Move to `hooks/snapshot-reminder.sh` and reference it.**

**B8. Anatomy docs duplicate protocol.** [docs/spec-anatomy.md](docs/spec-anatomy.md), [docs/us-anatomy.md](docs/us-anatomy.md), [docs/task-anatomy.md](docs/task-anatomy.md) overlap with [docs/protocol/spec-artifacts.md](docs/protocol/spec-artifacts.md). Anatomy docs are pedagogical (how to author a good spec); protocol doc is normative (schema). They should reference each other, not restate.

### Bucket C — Experience Gaps

**C1. No `--dry-run` for `/plan` or `/ship`.** Plan-mode short-circuit exists but isn't a flag — it depends on the user being in Plan Mode. A user wanting to preview the decomposition without firing 3 subagent invocations has no way. **Add `--dry-run` that prints the planned strategy and stops.**

**C2. No `--from-task <ID>` for `/ship`.** If task T-007 of US-3 fails after 3 iterations and the user fixes the spec, they re-run `/ship` and the whole feature re-ships from scratch. Cost goes up unnecessarily. **Add `--task <ID>` to ship a single task.**

**C3. Error messages bury "what to do next" inside long prose.** Example, [commands/plan.md:471](commands/plan.md:471): `"spec-$ARGUMENTS.md not found in input/specs/. Create the file (or use spec-driven mode by initializing with planr spec init and re-running)."` — two suggestions in one sentence with parens. The good error template is [docs/protocol/commands.md:62](docs/protocol/commands.md:62) ("Spec for slug 'X' not found... Run `planr spec create...`"). **Standardize error messages: 1 line "what" + 1 line "fix" + nothing else.**

**C4. No cost/token preview for `/ship`.** Opus 4.7 codegen across N tasks can run the user a non-trivial bill. The model could estimate (lines of spec + tasks × multiplier) and ask for confirmation if estimated > threshold. **Add a one-line preview ("Estimated 12 Opus tasks, ~80k tokens. Proceed?").**

**C5. `error-report.md` location is non-obvious in spec-driven mode.** It lives at `<SPEC_DIR>/tasks/error-report.md` (flat) — but if multiple tasks fail in the same feature, they all overwrite the same file ([commands/ship.md:101-102](commands/ship.md:101)). **Per-task path: `<SPEC_DIR>/tasks/T-NNN-error-report.md`.**

**C6. The Stop hook reminder text exposes implementation paths.** `[planr-pipeline] /ship aborted before snapshot — re-run /planr-pipeline:ship to refresh CLAUDE.md` ([hooks/hooks.json:9](hooks/hooks.json:9)) is fine, but if the user is on Cursor/Codex (the protocol claims runtime-agnosticism), this Stop hook never fires, and there's no equivalent. **Document the gap or add a one-line shell completion reminder for the other runtimes.**

**C7. First-time UX requires understanding 6+ markdown files.** README → spec.md.tpl → stack.md.tpl → docs/spec-anatomy.md → docs/rules.md → fix the auto-scaffolded TODOs. **A `--wizard` mode for `/plan` that asks 4 questions and writes a substantive spec body would close this.**

**C8. No status command.** A user who runs `/plan auth`, then `/ship auth`, then comes back two days later has no `/planr-pipeline:status auth` to see "tasks: 5 done, 1 failed (T-003), qa-report: pass". They must read the marker by hand.

**C9. Output formats inconsistent.** `/plan` emits a status block with `Mode:`, `Strategy:`, etc. as YAML-ish ([commands/plan.md:644-653](commands/plan.md:644)). `/ship` emits a similar block ([commands/ship.md:213-224](commands/ship.md:213)). Neither is machine-parseable. The `.pipeline-shipped` marker IS YAML ([docs/protocol/spec-artifacts.md:121](docs/protocol/spec-artifacts.md:121)). **Pick one: either summary blocks are YAML (`--json` flag) or stay prose; today's hybrid is awkward to grep.**

### Bucket E — Missing Architecture

**E1. No machine-checkable v1.0.0 schema artifact.** This is the biggest structural gap. A single JSON Schema (or Zod, or even a minimal validator script) would protect cross-runtime portability and let CI gate PRs. Lives at `docs/protocol/v1.0.0/schema.json` or `schemas/spec.schema.json`. Run by `conformance/runner.mjs --validate-schema <file>`.

**E2. No context handoff manifest between phases.** Today, agent N reads file system state to figure out what agent N-1 did. A `<SPEC_DIR>/.run-manifest.json` recording (a) which agents ran, (b) what they read, (c) what they wrote, (d) timing, (e) token cost would make debugging, resumability, and cost analysis tractable. Already partly there in `.pipeline-shipped` — but that's once-per-ship, not per-stage.

**E3. No rollback before /ship.** /ship writes to `src/`, project root (`docker-compose.yml`, `.env.example`, `Dockerfile.*`, `.github/workflows/ci.yml`), `Docs/`, and `CLAUDE.md`. A failed run leaves the user with `git reset --hard` as the recovery. **A `--snapshot-tag` option that creates `git tag pipeline-pre-ship-<feature>-<ts>` would cost nothing.**

**E4. No spec-quality gate.** [docs/spec-anatomy.md:121-128](docs/spec-anatomy.md:121) defines a "Completeness Score" and says "the Specification Agent evaluates spec completeness before decomposing." That's prose; no agent actually scores. A pre-decomposition spec-quality check (5-rule rubric: required sections present, ≥3 functional requirements, ≥3 GWT acceptance criteria, ≥1 business rule, no template TODOs left) would catch broken specs before expensive decomposition.

**E5. No plugin contract for custom agents.** Adding `mobile-agent` requires patching commands/plan.md, commands/ship.md, the docs/protocol/agent-roles.md table, the model-map, and rules.md. **Define an "agent registry" file (`agents/registry.yaml`) the orchestrator reads.**

**E6. No per-stage timing/cost log.** The conformance runner can verify state but not performance. A `<SPEC_DIR>/.run-log.jsonl` (one line per stage with `{stage, started_at, ended_at, model, tokens_in, tokens_out}`) is the minimum infra to do cost estimation in E1 above.

**E7. No locking for concurrent runs.** Two devs running `/ship` on the same feature at the same time will race on `src/`, `qa-report.md`, `.pipeline-shipped`. A `<SPEC_DIR>/.lock` file with PID/host would catch this. Low effort, high value at team scale.

## PHASE 3 — EXECUTION PLAN

### Sub-Agent 1 — ARCHITECT: proposed structure

Today's structure is "by file type" (`agents/`, `commands/`, `docs/`, `templates/`, `stacks/`). For this codebase, that is **the correct organisation** — each top-level dir maps to a concept the plugin runtime knows. The architectural problem isn't directory layout; it's **file size and content cohabitation**. So this isn't a tree rewrite — it's a tree refinement.

### Sub-Agent 6 — SCALABILITY STRATEGIST

**Scenario A: 10× spec complexity (20+ stories, 50+ tasks).**

- _Breaks:_ `specification-agent` decomposing 50 tasks in one Sonnet 4.6 call risks context-window fill and consistency loss. Today there's no chunking strategy.

- _Breaks:_ `qa-agent` walking 50 tasks' DoD lists in a single pass is slow and expensive.

- _Breaks:_ parallel /ship dispatch is only "within a US" per [docs/pipeline-overview.md:99](docs/pipeline-overview.md:99). 50 tasks across 20 US run sequentially-by-US, parallel-within-US — total wall time scales near-linearly.

- _Fix:_ introduce US-batch parallelism (medium refactor). Pre-compute the dependency DAG from US `DependsOn`/`Blocks` frontmatter. Run independent US in parallel.

- _Fix:_ spec-quality gate (E4) refuses giant single-spec decomposition; suggests splitting into multiple SPECs.

**Scenario B: Custom agent plugins (e.g. `mobile-agent`, `ml-agent`).**

- _Breaks:_ No plugin contract. Adding an agent today requires touching plugin manifest, both slash commands, all 4 protocol docs, the model-map, and rules.md. ≥10-file change.

- _Fix:_ `agents/registry.yaml` (E5) registers each agent with `phase`, `model_tier`, `dispatch_condition` (e.g. `task.type == "mobile"`). The orchestrator commands read this and dispatch generically. New agent = drop a file in `agents/` + add 5 lines to registry.yaml.

- _Estimated complexity:_ medium refactor (touches plan.md/ship.md orchestration logic but not subagent prompts).

**Scenario C: Team usage / concurrent runs.**

- _Breaks:_ No locking. Two devs running `/ship auth` in different terminals on the same `.planr/specs/SPEC-001-auth/` will race on `qa-report.md`, `.pipeline-shipped`, `src/`. Each will overwrite the other's marker. Worse: each will run frontend-agent + backend-agent in parallel, double-spending tokens, with neither seeing the other's edits.

- _Breaks:_ No worktree isolation. Both runs touch the same `src/`.

- _Fix (cheap):_ `<SPEC_DIR>/.lock` file with `{pid, host, started_at}`. /plan and /ship refuse to start if a lock exists less than N minutes old. Stop hook clears the lock.

- _Fix (better):_ recommend running /ship inside a git worktree (`git worktree add ../planr-auth feature/auth`). Document this in README.

- _Estimated complexity:_ small for the lock; documentation-only for worktree guidance.

### Section 3 — The Product Constitution

> _Save this as `docs/CONSTITUTION.md` once you accept it._

**What this product IS:**

A spec-driven AI software factory for Claude Code, runnable on Cursor and Codex via the same artifact contract — two commands (`/plan` then `/ship`), eight specialized subagents, a hard human-review gate between the two phases.

**What this product is NOT (three hard boundaries):**

1. **Not an agile-planning tool.** That's [planr](https://github.com/openplanr/OpenPlanr). The pipeline ships; planr plans. We do not own epics, sprints, or story-point estimation.

2. **Not a deployment tool.** [agents/devops-agent.md](agents/devops-agent.md) generates config; the pipeline never runs `docker compose up`, `kubectl apply`, or any cloud API. The user ships.

3. **Not a code reviewer.** The pipeline writes code per the task contract and runs build/test. It does not opine on code style beyond what the stack file declares.

**The 5 non-negotiable architecture rules:**

1. **The protocol is the contract; runtimes are adapters.** A SPEC authored on Claude Code MUST be byte-identical to a SPEC authored on Cursor or Codex (modulo timestamp). Anything that breaks this kills the value proposition.

2. **R1 is sacred.** PLAN and SHIP are two user invocations. No "auto-chain" flag. No "yolo mode." The human-review gate is the product.

3. **Tool restrictions are manifest-enforced where the runtime supports it.** Prompt-only restrictions are advisory and break under pressure. Claude Code is canonical because of this; Cursor/Codex are best-effort and conformance-tested.

4. **Schemas are machine-checkable, not prose.** Any artifact contract that can't be validated by a JSON Schema (or equivalent) drifts within two releases.

5. **Files over 300 lines are bugs.** This applies especially to slash commands and agent prompts: the model carries the whole file as context for every step. Split before adding.

**Definition of done for a new feature:**

- [ ] User-facing change documented in CHANGELOG.md

- [ ] If it's a new artifact: schema added under `schemas/v{X.Y.Z}/`, validated by conformance runner

- [ ] If it's a new agent: registered in `agents/registry.yaml`, tool restrictions explicit

- [ ] If it changes a command: `--dry-run` still works; `--json` output is updated

- [ ] Conformance fixture exercises the new path OR an explicit reason this isn't testable is in the PR description

- [ ] No file crosses the 300-line limit (if it does, split first, then add)

- [ ] `docs/rules.md` is normative — if a rule changes, every reference to it links there, not restates

**The standard for "too big a file":**

- Hard limit: 300 lines for any agent prompt or slash command

- Soft limit: 500 lines for any docs/protocol/\* file

- A doc over 500 lines is a sign the topic should be split into a directory

**The standard for "too complex a feature":**

- If the feature requires a new flag on both `/plan` and `/ship` AND new docs AND new schema fields AND new conformance fixtures — it's a v(N+1).0 release, not a patch. Don't sneak in feature creep on a doc PR.
